# Link2Chrome 单主实例与待机状态设计

日期：2026-07-15

## 目标

允许同一个 Link2Chrome 扩展同时安装并启用于多个 Chrome Profile 或 Chrome 实例，同时继续维持“一个 Browser Hub 只控制一个扩展实例”的现有模型。重复实例不得形成高速重连、状态闪动或无限日志增长。

## 范围

本次采用最小方案：

- 第一个成功连接 Hub 的扩展继续作为主实例。
- 后续连接收到现有的 WebSocket 关闭码 `1008` 和重复实例原因后，进入“待机”状态。
- 待机实例停止自动重连，Popup 明确显示“其他 Chrome 实例正在使用”。
- 用户点击 Popup 的“重新连接”后，待机实例进行一次新的连接尝试；如果主实例已经退出，它即可成为新的主实例。
- 普通网络中断、Hub 重启和 Chrome Service Worker 恢复仍使用原有指数退避重连。
- 重复连接日志同时在普通日志和操作日志中限流，避免再次产生 GB 级日志。

## 非目标

- 不同时控制多个 Chrome Profile。
- 不给 Session 增加浏览器实例标识。
- 不把现有 Session 自动迁移到另一个 Profile。
- 不在主实例断开后静默切换到另一个账号或 Profile。
- 不修改固定扩展 ID、端口或 Native Messaging 安装方式。

## 状态模型

扩展连接增加 `connectionConflict` 状态：

| 状态 | `wsConnected` | `connectionConflict` | 行为 |
|---|---:|---:|---|
| 已连接 | true | false | 正常接受 Hub 命令 |
| 普通断线 | false | false | 按指数退避自动重连 |
| 待机 | false | true | 不自动重连，等待用户手动尝试 |
| 已停用 | false | false | 不连接 Hub |

只有收到服务端明确的重复连接关闭码与原因时才能进入待机状态，其他 `1008` 协议错误仍按普通错误处理，避免掩盖真实故障。

## 数据流

1. 扩展连接 `ws://localhost:8765`。
2. Hub 没有主连接时接受该连接，扩展显示“已连接”。
3. Hub 已有主连接时，以 `1008 / duplicate Link2Chrome extension connection` 关闭新连接。
4. 新连接的扩展识别该关闭原因，设置 `connectionConflict=true`，停止心跳和自动重连。
5. Popup 显示“待机”，并保留“重新连接”按钮。
6. 用户手动重新连接时清除冲突状态并仅尝试一次；如果仍冲突，再次回到待机。

## 日志保护

- `WSManager` 的重复连接事件采用统一限流条件，例如前 3 次记录，之后每 50 次记录一次。
- 普通日志与 `OperationLogger` 使用同一个限流判断，不能只限流普通日志。
- 本次不删除现有日志；历史大文件由单独维护动作处理。

## 错误处理

- 待机不是“连接失败”，诊断信息应将它与 Hub 不存在、扩展 ID 不匹配区分开。
- 手动重连不能先显示永久成功；最终状态以 WebSocket 是否被 Hub 保留为准。
- 主实例断开时，Hub 回到无主状态，但不会主动唤醒待机实例；用户可在目标 Profile 中点击重新连接。
- 正在执行的命令遇到主连接断开时继续按现有逻辑失败，不重放写操作。

## 测试

测试文件继续放在项目 `test/` 目录：

- 服务端拒绝重复连接时仍保留原主连接，并验证操作日志限流。
- 扩展收到明确重复连接关闭原因后进入待机且不调用 `scheduleReconnect()`。
- 普通关闭仍调用指数退避重连。
- 手动重新连接会清除待机标记并尝试连接。
- Popup 对已连接、普通断线、待机、停用和扩展 ID 不匹配分别显示正确文案。
- 回归检查单实例连接、Hub 重启恢复和现有只读命令重试。

## 验收标准

- 两个兼容 Profile 同时启用扩展至少 10 分钟，不出现持续连接闪动。
- Hub 始终只保留一个主连接。
- 待机实例不产生持续重复连接日志。
- 操作日志不会因待机实例持续增长。
- 关闭主实例后，在另一个 Profile 手动重新连接即可恢复 MCP 控制。
